# Foreground chat refresh on push notifications

## Problem

Server-initiated Grit messages (post-workout reviews, missed-workout check-ins,
pre-workout check-ins, scheduled reminders) are generated by background jobs that
**insert into `chat_messages` + send a push notification**. The chat WebSocket
handler is per-connection with no broadcast hub, so a connected client is never
told about these messages live.

Combined with the frontend gating chat-history load behind a one-shot
`historyLoaded` flag, the result was: a review notification arrives, but the open
app's chat (and the unread tab badge) does **not** update until the app is
restarted (restart resets `historyLoaded`). Only *tapping* the notification
refreshed, because the tap path forces `setHistoryLoaded(false)` via
`openChatRequest`. A notification arriving while the app was foregrounded did
nothing at all — there was no `addNotificationReceivedListener`.

## Fix

Pull-on-push: when a chat-producing notification arrives in the foreground,
re-fetch chat history and bump the unread badge. No WebSocket hub rewrite.

- **`ProgramContext`** — new `chatRefreshSignal` counter + `notifyChatRefresh()`,
  mirroring the existing `programDataVersion` / `notifyProgramDataChanged` pattern.
- **`useNotifications`** — added a foreground `addNotificationReceivedListener`.
  For notification types that correspond to a persisted Grit chat message
  (`post_workout_review`, `missed_workout`, `pre_workout_checkin`, `reminder`,
  set `CHAT_MESSAGE_TYPES`) it calls `notifyChatRefresh()`. Tap behavior
  (`CHAT_OPEN_TYPES` → `requestOpenChat`) is unchanged. Listener is cleaned up
  alongside the existing response listener.
- **`useChatWebSocket`** — new `replaceHistory()` (ungated full replace) and
  `incrementUnread()`. `loadHistory()` (the one-shot first-open loader) now
  delegates to `replaceHistory()` behind its `historyLoadedRef` guard to avoid
  duplicated bodies.
- **`HomeScreen`** — centralized on a single `refreshChatHistory(bumpUnread)`
  helper that re-fetches `getChatHistory(25)` → `replaceHistory`, bumping unread
  when asked. An **apply-time** `isGritTypingRef` guard (checked inside `.then`,
  not at call time) drops the server snapshot if a send/stream started while the
  fetch was in flight, so it can't clobber the optimistic user message + live
  stream (neither persisted yet). Called from three triggers:
  - `chatRefreshSignal` effect (foreground push) — bumps unread when chat closed.
  - notification-tap (`openChatRequest`) effect — covers tap-while-already-open.
  - **focus-refetch fallback**: a `useFocusEffect` keyed on `chatOpen`.
    react-navigation re-runs it whenever `chatOpen` flips *or* the Home tab
    regains focus, so it fires on open, reopen, and tab-return-while-open. This
    is the path that works when push notifications are disabled (no foreground
    listener to lean on).

## Focus-refetch fallback (follow-up)

The push listener only helps when notifications are granted. Added a
notification-independent fallback so the chat self-heals on natural focus points,
plus a cleanup of the old one-shot load gating:

- Removed the `historyLoaded` state + its one-shot load effect from `HomeScreen`;
  loading now happens through the unified `refreshChatHistory` on first open (the
  `chatOpen` `useFocusEffect`).
- Removed the now-unused `loadHistory` helper and `historyLoadedRef` from
  `useChatWebSocket`; `replaceHistory` no longer touches that ref.
- `openProgramCreation` intentionally opens the chat *without* a refresh (it's a
  brand-new-program flow with no relevant history, and skipping avoids racing the
  scripted opening message).

## Why not a WebSocket broadcast hub

The per-connection WS handler has no userID-keyed registry; adding live server
push would require a hub plus notifying it from every background job. Pull-on-push
reuses the already-reliable history endpoint and the existing push delivery, so
it's proportionate to the bug.

## Notes / follow-ups

- `workout_reminder` is intentionally excluded from `CHAT_MESSAGE_TYPES` — it's a
  pure push with no associated chat message.
- Other screens (Home/History/ProgramDetail/Programs) already refresh correctly
  via `useFocusEffect` / `useFetchOnFocus` on navigation focus and via
  `programDataVersion` for in-app program edits; the gap was specifically
  push-driven server events while foregrounded.
- Pre-existing `tsc` error at `useNotifications.ts` `setNotificationHandler`
  (`NotificationBehavior` now wants `shouldShowBanner`/`shouldShowList`) is
  unrelated to this change and left untouched.
